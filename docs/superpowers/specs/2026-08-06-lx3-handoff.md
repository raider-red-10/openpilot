# 2026 Hyundai Palisade Hybrid (LX3) — findings and resolution

Handoff for the sunnypilot team. Everything below was measured on the vehicle unless marked
otherwise. Branch: `raider-red-10/openpilot @ lx3-unified`, `raider-red-10/opendbc @ lx3-unified`.

**Vehicles:** 2026 Hyundai Palisade Hybrid (HDA1 / LX3, `HYUNDAI_PALISADE_HEV_LX3`) and 2026 Kia
Sorento Hybrid (HDA2, `KIA_SORENTO_HEV_4TH_GEN_LFA2`), one comma device moved between them.
Goal was a single branch supporting both. The Sorento has a frozen `CarParams` regression test
(`test_lx3_regression.py`) that has passed continuously throughout.

## How HDA1 and HDA2 live on one branch

This is the part worth understanding first, because it is why a single branch works at all and
what constrains every change below.

**HDA1 vs HDA2 is not a branch or a platform property — it is detected at runtime from live
CAN.** `interface.py` looks at what the camera is sending:

```python
lka_steering = 0x50 in fingerprint[cam_can] or 0x110 in fingerprint[cam_can]
```

A camera that sends `LKAS` (`0x50`) or `LKAS_ALT` (`0x110`) is HDA2 — openpilot's steering
command is forwarded to an ADAS ECU which retransmits it. A camera that does not is HDA1, and
the camera talks to the MDPS directly. From that one probe, `CanBus` assigns A-CAN and E-CAN
differently, `CANFD_LKA_STEER_MSG` is set, and the whole downstream configuration follows.

The practical consequence: **the same binary configures itself for whichever car it is plugged
into — including on a swap, with no manual step.** *Identity* was never actually at risk
across boots: `CarParamsCache` is `CLEAR_ON_MANAGER_START`, so every boot does a full FW
fingerprint regardless (verified in the device's swaglog history — every boot on record says
"Getting VIN & FW versions", never "Using cached CarParams"). Two changes complete the
zero-touch story anyway: the cache is now validated against a live VIN read in the one path
where it *is* consumed (a card restart within a boot — it was trusted blindly there), and
`calibrationd` discards the camera calibration when the `carFingerprint` changed since the
last drive — joining `paramsd`/`torqued`/`lagd`, which already did this for their learned
state. See *Swapping cars: the calibration hazard* below for why that last one matters and
how it was measured. `tools/lx3/swap_car.py` remains as a manual force-clear for debugging.

### The three steering paths

| path | message | used by |
|---|---|---|
| LKA steering (HDA2) | `LKAS` `0x50` / `LKAS_ALT` `0x110` on A-CAN | Sorento |
| LFA steering, torque | `LFA` `0x12A` on E-CAN | most CAN FD Hyundais |
| LFA steering, **angle** | `LFA_ALT` `0xCB` on E-CAN | **Palisade (LX3)** — added here |

`LFA_ALT` is the HDA1 angle-steering path and did not exist on the base branch. The ordering in
`create_steering_messages()` matters: **the LKA branch is checked first**, so an HDA2 car exits
before the `LFA_ALT` branch is ever evaluated. `test_lfa_alt.py` pins that — it asserts `0xCB` is
unreachable on an LKA-steering car.

`SEND_LFA` is set from `0xCB in fingerprint[CAN.CAM]`, so this too is runtime detection rather
than a per-car declaration.

### CCNC is orthogonal

`HyundaiFlags.CCNC` (`2**28`, safety param `2048`) describes the Connected Car Navigation
Cockpit cluster, not the steering architecture. It gates cluster message retransmission
(`0x161`, `0x162`), the LFA button living in its own message, and several RX-check
accommodations. All twelve non-HDA2 CCNC cars already in the port are **torque** steering; the
Palisade is the first `CANFD_ANGLE_STEERING` CCNC car, which is why so many of its quirks were
unexercised.

### Keeping the working car working

The Sorento was working perfectly before any of this and had to stay that way. Two mechanisms:

- **A frozen baseline.** `sorento_baseline.json` captures the Sorento's resolved `CarParams` —
  flags, safety params, alpha-long availability — for *both* camera probes (`0x50` and `0x110`),
  since the real vehicle's LKAS address was not known. `test_lx3_regression.py` asserts both are
  byte-identical after every change. It has passed continuously.
- **Scoping by the narrowest correct condition.** New behaviour is gated on the fingerprint,
  `CCNC`, or `CANFD_ANGLE_STEERING` rather than added to shared paths. Where shared code did have
  to change, it is called out in *Changes that touch shared code* below.

Panda follows the same pattern: TX message lists are selected at runtime from
`hyundai_camera_scc` + `get_hyundai_ccnc()` + `hyundai_longitudinal`, and LX3-specific
allowances (`0xCB`, `0x1AA`, `0x10B`) live only in the CCNC camera-SCC list. That scoping is what
kept an earlier `0xCB` change from breaking 48 unrelated safety tests once it was moved out of
the shared macro.

### What this cost, and where it bit

The runtime-detection approach is right, but it means a car can differ from its siblings in ways
nothing declares. Every bug in this document is of that shape: a message that exists on other
cars but is empty here, a counter that steps by 2 instead of 1, a sentinel value nothing else
reads, an address absent from a check list. None of it is visible from the platform config —
only from the bus.

## Measured quirks of this platform

These are the reusable findings. Several are likely to affect other CCNC / HDA1 CAN FD cars.

### Turn signals are not in `BLINKERS` (0x413)

`0x413` is absent. The lamps are in **`0x3e3` byte 11 — bit 2 left, bit 4 right**, at 5 Hz.
Same two-bits-apart layout `BLINKERS` uses. Confirmed live: each bit toggles at 1.32 Hz for its
own stalk and is static for the other.

Because the message is 5 Hz rather than 50 Hz, the `update_blinker_from_lamp` hold had to be
raised from 50 to 100 frames: sampling a 379 ms lamp pulse every 196 ms leaves up to 588 ms
(59 frames) between two frames that catch the lamp lit, so 50 drops the blinker between flashes
and cancels a lane change mid-manoeuvre.

Only the two lamp bits are declared. `0x3e3` carries an unidentified checksum and counter, and
declaring either makes the parser validate it and silently drop every frame on a mismatch.

### Cruise buttons are not in `CRUISE_BUTTONS_ALT` (0x1aa)

This car populates `0x1aa`'s button field with **zeros**. The real buttons are in
**`LFA_BUTTON_ALT` (0x10b) byte 10**, at 25 Hz:

| bit | button |
|---|---|
| 0 | `+` |
| 1 | `−` |
| 2 | `resume` |
| 3 | cancel/set toggle — sets to current speed when cruise has no set speed, cancels when it has one (`VSetDis` 255 ↔ value) |
| 7 | LFA |

Note `+` and `resume` are **separate buttons** here, unlike most Hyundais where `RES_ACCEL`
serves as both. They map to separate `ButtonType`s.

Consequence before the fix: openpilot generated **no cruise `buttonEvent` at all**, so Speed
Limit Assist could never see a confirm press — `plusHold` stayed `0.0` for an entire drive.

### The SCC reports `VSetDis = 255` when it has no set speed

Passed through as a real speed it becomes 255 mph (410 kph); the planner clamps that to
`V_CRUISE_MAX` and ICBM spends the drive pressing buttons to drag the car to **90 mph**.
openpilot only special-cases `0` and `-1`, so 255 is now normalised onto `0`.

Only visible where openpilot reads `cruiseState.speed` while the car's cruise is **off**, which
is exactly what ICBM owning the set speed requires. Cars that let the PCM own the set speed only
read it while engaged, so the sentinel never surfaces there.

### Counters on this platform step by 2

`0x105` (already known), `0x130`, and `0x10b` all advance their counter by **2 per frame**. The
safety layer's counter check hardcodes `+1` and can never be satisfied, so these need
`.max_counter = 0, .ignore_counter = true`. The DBC-side parser needs the same treatment or
`can_valid` drops.

### The camera speed limit is on the camera bus, not E-CAN

`carstate_ext.update_speed_limit` reads `FR_CMR_02_100ms` (`0x1fa`) from the E-CAN parser on
LKA-steering cars and from the **camera** parser on everything else — but availability was
always decided by looking for `0x1fa` on E-CAN. On an LFA-steering car the message is on bus 2,
so `SPEED_LIMIT_AVAILABLE` was never set and `carStateSP.speedLimit` stayed 0. The gate now
checks whichever bus the read uses. Verified: `0x1fa` appears on bus 2 only, ~10 Hz.

### `0x10b` was never in panda's RX check list

panda's rx hook only runs for addresses in `rx_checks`. `0x10b` was not there, so **the entire
`0x10b` branch had never executed** — including a MADS button read added earlier in this project.

This mattered far beyond MADS. On a non-longitudinal Hyundai, `controls_allowed` latches only on
the cruise-engaged rising edge *and* with a recent user button press:

```c
if (cruise_engaged && !cruise_engaged_prev && (hyundai_last_button_interaction < HYUNDAI_PREV_BUTTON_SAMPLES)) {
  controls_allowed = true;
}
```

`hyundai_last_button_interaction` was fed from `0x1aa` — always zero on this car — so it
saturated permanently, `controls_allowed` never latched, and **every button ICBM transmitted was
rejected by our own tx check**. Also note `is_msg_valid()` clears `controls_allowed` outright on
an invalid frame, so a badly-declared RX check is actively harmful, not merely inert.

Fixing the RX check was necessary but not sufficient — the same empty-`0x1aa` trait broke the
latch two more ways (the openpilot heartbeat and the toggle-button engagement); the full chain
is in *How the set speed was fixed* below.

## How the set speed was fixed

Resolved 2026-08-06, road-verified: the set speed walks straight to limit+offset and stops on
it. Three stacked causes, found by recording a full drive with `tools/lx3/capture.py` and
correlating openpilot's send requests, panda's accept/reject verdicts, and the SCC's reported
set speed offline. The original hypotheses resolved as: injection works, the camera is the
right receiver, and every failure was our own safety layer.

**Diagnosis shortcut for next time:** pandad marks safety-rejected `sendcan` frames with
`src = 192 + bus` in the `can` stream. One capture showed 1109 of 1132 button frames rejected
— the discriminating fact the debug logs upstream of the panda could never show.

### Cause 1: the press was a 1 ms blip

All press frames were queued in a single 100 Hz control cycle, so the "160 ms press" hit the
wire in ~1 ms and the module's continuing 25 Hz idle stream contradicted it within 40 ms. Fixed
by pacing injection to the genuine stream: one frame per fresh `0x10b` frame, each riding one
counter step ahead of the frame it follows (`create_lx3_press_messages` in opendbc `icbm.py`).

### Cause 2: the panda heartbeat killed `controls_allowed` every ~2.5 s

The wire capture showed `controls_allowed` latching correctly on each cruise-engage rising
edge, then dying 2.5 s later, every time. That is `main.c`'s heartbeat protection: three 1 Hz
heartbeats reporting "openpilot not engaged" while `controls_allowed` is set force-clear it.
openpilot never reported itself engaged because `blockPcmEnable` keys off
`recent_button_interaction()`, whose deque was fed from `CRUISE_BUTTONS_ALT` (`0x1aa`) — always
zero on this car. The empty-`0x1aa` quirk, striking a third time. Fixed by feeding the deque
from the real buttons in `0x10b` (`_update_lx3_buttons` in carstate), which also makes
openpilot engage/report like every other stock-long Hyundai. The deque only appends on a fresh
frame (counter advanced) so its window spans the same ~320 ms as panda's own 8-sample check.

### Cause 3: engaging with the set/cancel toggle never latched at all

Byte 10 bit 3 is a cancel/set toggle: with no set speed it sets to the current speed, with one
it cancels (`VSetDis` 255 ↔ value on the vehicle). Panda mapped it to no button, so cruise
engagements made with it produced a rising edge with no "recent interaction" and
`controls_allowed` never latched — sessions where ICBM had zero effect for minutes. Fixed by
mapping it to `HYUNDAI_BTN_CANCEL` in the rx hook. On the openpilot side it joins the
interaction deque as `Buttons.CANCEL` but deliberately emits **no** `ButtonEvent` — a cancel
event would read as a user disengage request at the moment the driver engages.

### And one calibration: this SCC counts every injected frame as a press

A driver's press holds the bit across 2–5 consecutive frames of the module's own stream and
counts once. Injected frames interleave with the module's idle stream, so the SCC sees a
release after each one and counts each frame individually — 11 accepted pressed frames moved
the set speed by 10. `LX3_PRESS_FRAMES` is therefore **1**: one frame = one step, presses
spaced by `BUTTON_REPEAT_S`, and ICBM's closed loop lands exactly on target at ~4 mph/s.

## Swapping cars: the calibration hazard

Found 2026-08-07, after one swap was driven without the manual clear. The failure is worth
understanding because **openpilot's own sanity checks cannot catch it**, and any multi-car
device will eventually hit it.

**What happened.** The device moved Palisade → Sorento without clearing learned state. Identity
resolved correctly (see above — FW fingerprinting runs every boot), but `CalibrationParams`
survived the swap: the Sorento drove on the Palisade's camera calibration, and calibrationd
*updated* that calibration with Sorento data as it drove — producing a fully "valid" 50-block
blend belonging to neither car.

**The symptom.** A persistent lane offset — the car rode visibly too far right — with no
alert of any kind. Every calibration value was individually inside the accepted ranges; the
calibration was wrong for the car, not wrong on its face.

**Measured.** Blended calibration vs. the fresh one relearned after a manual clear on the same
car, same mount:

| | roll | pitch | yaw |
|---|---|---|---|
| blend (50 blocks) | −0.0001 | **0.048** | 0.0166 |
| fresh Sorento (early) | 0.0001 | **0.0371** | 0.0186 |

The contamination fingerprint is the **pitch: 0.62° off**. A pitch error tilts the perceived
ground plane, skewing where lane lines project laterally at the planning distance. (Yaw — the
axis usually blamed for lane offset — was essentially unchanged; on this pair of cars the
blend lived in pitch. Ride quality confirmed fixed immediately after the clear + recal.)

**The fix.** `calibrationd` now discards `CalibrationParams` when `CarParamsPrevRoute`'s
`carFingerprint` differs from the current car — the same self-invalidation idiom
`paramsd`/`torqued`/`lagd` already use for their learned state (calibrationd was the one
consumer missing it). One limitation: the reset triggers on the car-change *boundary*, so it
cannot retroactively clean contamination from swaps driven before the fix existed — that one
case needs a single manual `params.remove("CalibrationParams")`.

Also fixed in passing: `swap_car.py` cleared the legacy `LiveParameters` key while `paramsd`
actually reads `LiveParametersV2`.

**Verification status.** Sorento verified on the road after the manual clear (ride returned to
normal, fresh calibration converging). The first post-swap Palisade drive is the automatic
reset's first road test: "Calibration in Progress" appearing on its own at drive start is the
proof it fired.

## Tools (all in `tools/lx3/`, none require special modes unless noted)

| Tool | Purpose |
|---|---|
| `capture.py` | Record all CAN plus everything openpilot asks the panda to send, to `/data/lx3_capture.bin.gz`. ~1 MB/min. |
| `replay.py` | Answer questions from a capture offline: `summary`, `msg <addr>`, `diff <addr> <byte>`, `press`, `tx`. Recovers truncated files. |
| `blinker_scan.py` | Differential scan that found the turn signals. Also has a `watch` mode for one bit and a whole-byte mode. |
| `button_scan.py` | Same technique, adapted for cruise buttons. |
| `frame_diff.py` | Full-frame idle vs press diff. |
| `button_probe.py` | Raw button field alongside `carState.buttonEvents`. |
| `tx_probe.py` | Does openpilot's frame reach the wire — `sendcan` vs transmit echo. |
| `checksum_check.py` | Whether an address carries the standard HKG CAN FD checksum, with a known-good control. |
| `sla_trace.py` | Speed Limit Assist chain state during a drive. |
| `vcruise_probe.py` | Replay live `carState` through `VCruiseHelper` branch logic. |
| `swap_car.py` | Manual force-clear of per-vehicle identity and learned params. No longer needed for swaps (see *Swapping cars*); kept for debugging and for cleaning contamination that predates the automatic reset. |

**In-code instrumentation:** removed after the resolution, as planned. If it is ever needed
again, it lived in `openpilot/sunnypilot/selfdrive/car/lx3_debug.py` (git history) — no-op
unless `/data/lx3_debug` existed, with call sites in `cruise.py`, `speed_limit_assist.py`,
ICBM `controller.py`, and opendbc `icbm.py`. The capture/replay pair above answers most
questions without it: in particular `replay.py tx` distinguishes queued vs rejected vs
transmitted, which is the question the in-code logs could not answer.

### The differential scan method

Used three times successfully (LFA button, turn signals, cruise buttons). Two things matter:

- **Discriminate on change, not level.** "Was this bit ever set" matches every counter and
  checksum on the bus and returns hundreds of false hits. "Changed during this phase and never
  while idle" returns a handful.
- **Accumulate frames as integer bitmasks.** Per-bit Python cannot keep up with CAN FD; the
  queue saturates, `drain_sock` stops returning, and each phase silently records the previous
  phase's backlog.

Hyundai CAN FD puts `CHECKSUM` in bytes 0–1 and `COUNTER` in byte 2 — a dozen messages reporting
"byte 2 bit 7" is the counter rolling, not a signal.

## Test coverage added

The upstream Speed Limit Assist suite forces `openpilotLongitudinalControl = True`, so
`update_state_machine_non_pcm_long` — the path every stock-longitudinal ICBM car takes — had
**no coverage**. That is where most of these bugs lived.

- `test_speed_limit_assist_non_pcm.py` — the confirm handshake, offline
- `test_speed_limit_assist_chain.py` — VCruiseHelper + assist + planner + ICBM + a simulated car,
  as a loop. Also pins the engaged-before-set-speed race
- `test_set_speed_management_engaged.py` — engagement fallback and set-speed seeding
- `test_lx3_buttons.py` — button decode, plus `TestLx3ButtonInteraction`: the interaction-deque
  feed that keeps the heartbeat alive (window freshness, toggle-as-interaction, no duplicate
  or spurious events)
- `test_lx3_button_press_shape.py`, `test_lx3_press_cadence.py` — the one-frame press, its
  byte-exactness, counter riding, pacing against the genuine stream, press completion, and the
  repeat gap
- `test_blinkers_alt.py`, `test_speed_limit_available.py`, `test_cruise_set_speed_sentinel.py`
- `TestHyundaiCanfdCcncAltButtonsTx` in `test_hyundai_canfd.py` — the CCNC safety config had
  **zero** panda coverage before this; now also pins the `controls_allowed` latch from every
  `0x10b` button including the toggle, and that no latch happens without a recent button

Totals at handoff: 7708 safety, 877 car, 382 sunnypilot (passed; subtests excluded). The one
failing car test is `test_test_route_present` — this platform has no uploaded comma route, and
it has failed since the platform was added.

## Changes that touch shared code

Worth review, since they affect cars other than this one.

- `set_speed_management_engaged()` in `cruise_helpers.py` — ICBM and Speed Limit Assist gate on
  `carControl.enabled`, which never goes true on a MADS car engaged laterally. Falls back to the
  car's own cruise, scoped to where ICBM owns the set speed. Only ever widens the condition.
- `VSetDis >= 255 → 0` in Hyundai carstate — affects any Hyundai CAN FD car.
- `_seed_v_cruise_from_car()` in `cruise.py` — seeds openpilot's set speed from the car's on
  pcmCruise cars where ICBM owns it. Guarded to that configuration.
- `initialize_v_cruise` returns early on `pcmCruise`, which is why an earlier seeding attempt
  was a silent no-op. Worth knowing if anyone else tries this.
- `HYST_GAP = 0.0` in `icbm/controller.py` is a known upstream defect —`apply_hysteresis` with a
  zero gap is a pass-through. Deliberately **not** changed: the Sorento runs ICBM at this value
  without trouble and it is shared tuning.
- `get_minimum_set_speed()` returns display units (20 mph / 30 kph) but `VCruiseHelper` clips a
  **kph** value against it. Harmless as a lower bound today. Not fixed.

## Who can run this, and what porting another car takes

**Another 2026 Palisade Hybrid (HDA1 / LX3):** works as-is once its firmware versions are added
to `fingerprints.py` — that is all "getting fingerprinted" needs to accomplish. Every
LX3-specific behaviour keys off the platform that fingerprinting selects.

**HDA2 cars (Sorento, etc.):** unchanged by this work — that is what the frozen baseline and
the narrow scoping were for. Whatever sunnypilot already supported still holds.

**A different HDA1 / CCNC car (non-hybrid Palisade, other models):** the port is now
trait-based — see `2026-08-06-hda1-trait-flags-design.md`. Everything bus-detectable
configures itself from the fingerprint at identification time: HDA1 vs HDA2, the `LFA_ALT`
angle path, blinkers in `0x3e3` (auto-detected from `0x413` absence), and the missing
doors/hands-on-detection messages. The one thing a new car must *declare* — because it is
content-defined and drives panda safety behaviour — is `HyundaiFlagsSP.BTN_CLUSTER_0X10B`:
"the steering-wheel cluster is in `LFA_BUTTON_ALT` byte 10 and `0x1aa` is vestigial." Measure
it with the `tools/lx3/` scanners, add the platform to the declaration list in
`_get_params_sp`, done. No `carFingerprint` checks remain anywhere in the port.

**The panda asymmetry is resolved:** the `0x10b` behaviour (rx button reads, the RX check,
and the TX allowance) is gated on `HyundaiSafetyFlagsSP.BTN_CLUSTER_0X10B = 16` on
`safetyParamSP` — the mirror of the openpilot flag — not on CCNC. CCNC cars without the bit
keep stock alt-buttons handling (pinned by `TestHyundaiCanfdCcncWithoutBtnCluster`), so the
twelve existing torque CCNC cars are unaffected by this branch.

## Remaining loose ends

Everything in the *Working* table is road-verified, including Speed Limit Assist adjusting the
set speed to limit+offset. What's left is polish, not function:

- Two road verifications outstanding on the first post-swap Palisade drive: "Calibration in
  Progress" appearing on its own (proves the calibrationd car-change reset), and the set
  speed walking to limit+offset again under the trait-flags build (behavior is identical by
  construction and pinned by tests; the `safetyParamSP` value changed, so one confirmation
  drive is due diligence).
- `test_test_route_present` still fails — this platform has no uploaded comma route.
- `HYST_GAP = 0.0` and the `get_minimum_set_speed()` unit mismatch above remain deliberately
  untouched (shared tuning / harmless).
- The changes worth upstream review are listed under *Changes that touch shared code*, plus
  the trait mechanism itself (`BTN_CLUSTER_0X10B` flag + safety bit, and the auto-detected
  blinker/absence flags) — scoped, symmetric across openpilot and panda, and test-covered.
- Update flow gotcha that cost one wasted test drive: the device build pins opendbc, so a
  deploy needs *both* repos pushed and `git submodule update --init opendbc_repo` on the
  device after the reset — a plain `git reset --hard` leaves the old opendbc (and therefore
  the old panda safety code) in place with no error.
